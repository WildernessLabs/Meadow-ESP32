# File Generator

`FileGenerator` is a .NET Core application that will generate a number of C#, C and C++ files for inclusion in other Meadow projects, namely, Meadow.Core, ESP32 application and NuttX.  The application guarantees consistency between a number of items use by all three systems, namely:

* Enums used to identify interfaces, message type, functions etc.
* Message structures
* System independent encoding and decoding of the message structures

## Input Files

The `FileGenerator` application takes two input files:

* `SharedEnums.json`
* `Messages.json`

These files define the structures and constants that will be stared between the three systems.

### `SharedEnums.json`

Shared enums / constants can take two forms:

* Free form values
* Name value pairs

Free form values are used when there is no requirement for a name to have a specific value.  For instance, the _Interface_ identifier does not need a set value for say `WiFi`, the only requirement is that all three system use the same value for the WiFi interface.

Name value pairs are used when one of the systems uses a specific value (for instance `WiFiAuthenticationMode`) or we wish to use flags (`MessageTypes`).

In the case of `WiFiAuthenticationMode` the value is defined by the ESP32 definitions.

`MessageTypes` are an implementation design decision to use flags to allow for the values to be combined later if needed.

### `Messages.json`

The format of the message can be found in the [message format document](MessageFormat.md).  Part of the message is an optional payload.  The `messages.json` file contains the definition of the message payloads.

Most of the message payloads are specific.  For example, it is hard to see the `WiFiCredentials` payload being used for any purpose other than connecting to a WiFi access point.  Other messages such as `IntegerResponse` and `IntegerAndErrnoResponse` have multiple uses as they are common responses to POSIX API calls.

The convention that is used is for a request & response payload to have two corresponding message payload definitions.  Take the `read` POSIX API.  The two messages associated with it:

* `ReadRequest`
* `ReadResponse`

The exceptions are POSIX APIs such as `write`.  This uses the `WriteRequest` for the initial request but uses the `IntegerAndErrnoResponse` payload for the response.  This is common to several POSIX APIs.

As well as generating the message structures for the three languages, `FileGenerator` also generates three methods to support the transportation of the data between the systems:

* Encode
* Extract
* Encoded message length

Consider the `ConfigurationValue` message.  This takes an ID for the value to be set and a BOB object containing the data for the value.  Configuration values can be integers, booleans strings etc. hence the use of a BLOB to transfer the value.

The `ConfigurationValue` message will generate the following methods:

* `EncodeConfigurationValue`
* `ExtractConfigurationValue`
* `EncodedConfigurationValueBufferSize`

The names vary between the systems but the principle remains the same across all of the systems.

The encode method will take a message and encode the method into a block of memory.  Similarly, the extract method will take a block of memory and populate a message structure with the data that was encoded.

The encoded buffer size allows an appropriate memory block to be made available to hold a specific instance of a message.  This method takes into account the fact that strings and binary blocks of data (of variable length) are possible message elements.

## Output Files

The files generated by the application are first placed in an `Output` directory located in the source directory.  These files are then copied into target project directories.  The `Output` directory will be created if it does not exist.

C# files for use in Meadow.Core:

```
Messages.cs
Encoders.cs
SharedEnums.cs
```

C++ files for the ESP32 microcontroller:

```
Encoders.cpp
Encoders.hpp
SharedEnums.hpp
```

C files for the coprocessor code running as part of NuttX:

```
espcp_encoders.c
espcp_encoders.hpp
espcp_shared_enums.h
```

### Environment Variables

The application uses two environment variables to indicate the location of the source code for the coprocessor code in Meadow.Core and Nuttx.

* `EspcpSourceDirectory` - Location of the C source files within NuttX
* `MeadowCoreSourceDirectory` - Location of the C# source files within Meadow.Core

The source files will be copied from the `Output` directory into the relevant source directory.  The source for MeadowCore is derived from the `FileGenerator` source directory.

## Running the Application

As noted, this application is a .NET Core application and is run by opening a console window, changing to the application directory and executing the command:

`dotnet run`
