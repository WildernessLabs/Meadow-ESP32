# Test Automation Plan

Planning notes for automating the MeadowComms unit test suite. The build, run and
debug scripts described here are in the repository, and the emulated tier runs in CI.
What remains are the firmware changes listed towards the end and the hardware tier.
For how to use the scripts see [Testing](Testing.md).

**Verification status (15 September 2026).** The emulated and hardware tiers have
both been exercised end to end. Results are recorded inline and marked **Verified**;
anything still unproven is marked **Unverified**. Testing used ESP-IDF 5.5.3,
`qemu-xtensa` `esp_develop_9.2.2_20250817`, and an ESP32 dev board (chip rev v3.1).

**Tooling.** `build.sh --qemu` generates the emulator image, `qemu.sh` boots it for
interactive use or debugging, and `test/run-tests.sh` drives the test menu on either
QEMU or a board. `run-tests-ci.sh` wraps all of that for the `Unit tests` workflow.

## Purpose

The test suite in `components/F7Services/test/` is currently driven by hand: build,
flash, open a serial monitor, press ENTER, type a test number. This document records
what it would take to drive that process from a script, which parts of the suite can
realistically run unattended, and what needs to change in the firmware and build to
make that practical.

## Build Prerequisites

**Verified.** The test build does not stand alone. On a clean checkout
`test/build.sh --build` fails twice before it reaches a compiler, and both failures
are invisible in a working tree that has already built the main application.

| Blocker | Cause |
|---|---|
| `Include directory '<root>/build/config' is not a directory` | `test/main/CMakeLists.txt:1` adds `../../build/config` as an include directory. That path is generated by the **root** application build. |
| `fatal error: build_info.h: No such file or directory` | `main/version.h:12` includes `build_info.h`, which only the **root** `build.sh` generates (line 260). `test/build.sh` has no equivalent step. |

Both clear if the root project is built (or at least reconfigured) first, which is why
a developer machine never sees them. Any CI job must do the same, or the test build
needs decoupling from the root build.

A related correctness risk sits behind the first blocker: the test build ends up with
both the root `build/config/sdkconfig.h` and its own `test/build/config/sdkconfig.h`
on the include path, and the two are generated from different defaults. Whichever
resolves first wins. This has not been shown to cause a failure, but it means the test
binary may not be compiled against the configuration its own `sdkconfig.defaults`
describes. **Unverified** — worth confirming before relying on it either way.

The settings are read from `unittest.config.json` on the device, written there by
`mkfsimage.sh` (gitignored; the template is not).
The `[WiFi]` tests need real credentials there, but every other tier only needs the
file to exist, so a hosted CI job can supply a dummy.

## The Automation Surface

`unity_run_menu()` is ESP-IDF's standard interactive runner and is already a
scriptable protocol — no firmware change is needed to drive it:

| Input | Effect |
|---|---|
| `<Enter>` | Print the list of registered tests |
| `3` | Run test number 3 |
| `[FileSystem]` | Run every test carrying that tag |
| `*` | Run all registered tests |
| `"Delete file"` | Run a single test by name |

`UNITY_BEGIN()` / `UNITY_END()` bracket the run with a machine-readable summary
(`N Tests M Failures K Ignored`) alongside per-test `PASS` / `FAIL` lines.

**Verified**: the same driver logic works unchanged against QEMU and hardware. Only
the transport differs — a TCP socket in one case, a serial port in the other.

### Driving the Menu Correctly

A runner must wait for the menu prompt `Enter next test, or 'enter' to see menu`
before sending the next selector — **not** the Unity summary line. The summary is
printed some time before the device calls `unity_gets()`, and that call flushes the RX
buffer (see [Supplying Data to a Test](#supplying-data-to-a-test)). A selector sent on
seeing the summary is silently discarded and the run appears to hang.

This is not theoretical: the proof-of-concept runner made exactly this mistake and
produced a false "stall" that initially looked like a firmware defect.

## Test Classification

The existing tags are organised by subsystem, which is the right way to write tests but
not the way a runner needs to select them. What a runner cares about is whether a test
can complete without human or hardware assistance.

| Tag | Cases | QEMU | Hardware | Notes |
|---|---|---|---|---|
| `[NvsManager]` | 1 | **Pass** | **Pass** | Tagged `[Emulated]` |
| `[FileSystem]` | 11 | **11/11 pass** | **11/11 pass** | 10 tagged `[Emulated]`; the full-filesystem test is `[Slow]` |
| `[System]` | 1 | **Stalls** | **Pass** (288 mV) | Hardware only |
| `[CoreDump]` | 4 | Unverified | Unverified | Ordered sequence; one case panics deliberately |
| `[WiFi]` | 10 | No (no radio) | Unverified | Needs a live access point |
| `[Bluetooth]` | 10 | No (no radio) | Unverified | One case needs an external BLE client; one runs 4–5 minutes |
| `[Helpers]` | 2 | Restart only | Unverified | Heap tracing needs OpenOCD and JTAG |

### Tests Needing Special Handling

- **Client-driven.** `TestBluetooth.cpp:806` ("number of iterations controlled by
  client") requires a BLE peer. `WriteNumberCharacteristicSoakTest.py` is that peer.
  Automating it means orchestrating both sides together, not driving the menu.
- **Self-rebooting.** `TestCoreDump.cpp:370` asserts deliberately to produce a core
  dump; `TestHelpers.cpp:32` restarts the device. The runner must expect the reboot
  and resynchronise with a fresh menu rather than treating silence as a hang.
- **Ordered and stateful.** The four `[CoreDump]` cases form a sequence
  (generate → information → fragment → erase). The two file system upgrade cases carry
  state across a reflash.
- **Long running.** `TestBluetooth.cpp` restarts the Bluetooth service
  `BluetoothRestartIterations` times, 50 by default, taking 4–5 minutes on its own. A full `*` sweep is not a per-commit check. The
  `[Slow]` tag exists for this; the Bluetooth case is a candidate for it.
- **Slow only under emulation.** `WriteFile returns Failure on a full filesystem`
  fills the partition a block at a time. That is seconds on hardware and minutes under
  QEMU, where it exceeded a ten minute timeout on a shared build runner, so it is
  tagged `[Slow]` and excluded from CI. Emulated flash is the slowest thing QEMU
  models; tests dominated by flash writes belong on hardware.
- **Environmental.** The `[WiFi]` cases pass or fail partly on the RF environment
  rather than on the firmware. A policy for this is needed before they join any
  automated set, otherwise routine red builds will train everyone to ignore the runner.

## Resolved Defect: LittleFS Double Mount

**Fixed.** `[FileSystem]` now passes 11 of 11 on both QEMU and hardware.

Running `TEST_CASE("Mount failure when already mounted")`
(`TestFileSystem.cpp:684`) used to panic the **next** test to touch the file system,
stopping the tag at 9 of 11. It reproduced on hardware and under QEMU with
byte-for-byte identical backtraces:

```
Guru Meditation Error: Core 0 panic'ed (LoadProhibited)
EXCVADDR: 0x80000008

TestFileSystem.cpp:737   fs->ReadFile(...)
FileSystem.cpp:292         stat()
esp_littlefs.c:1349        vfs_littlefs_stat
esp_littlefs.c:691         sem_take
queue.c:817                xQueueTakeMutexRecursive   <-- freed context
```

The cause is in the `joltwallet/littlefs` component. `esp_littlefs_init()` rejects a
duplicate registration like this:

```c
if (esp_littlefs_by_label(conf->partition_label, &index) == ESP_OK) {
    ESP_LOGE(ESP_LITTLEFS_TAG, "Partition already used");
    err = ESP_ERR_INVALID_STATE;
    goto exit;
}
...
exit:
    if(err != ESP_OK){
        if( index >= 0 ) {
            esp_littlefs_free(&_efs[index]);
```

`esp_littlefs_by_label()` sets `index` to the slot of the **existing** mount, so the
error path frees that live context, including the lock, while the VFS is still
registered against it. Any subsequent file operation then locks freed memory. The same
defect surfaced once as a `Cache error` rather than `LoadProhibited`, so do not triage
it from a single panic type.

The fix is in `FileSystem::Mount()`, which now refuses to register a partition that is
already mounted so the faulty path is never entered. It was deliberately not applied to
the component itself: `managed_components/` is fetched from the component registry and
a local edit there would be lost the next time dependencies are resolved. The upstream
defect is still present in `joltwallet/littlefs` 1.5.5 and is worth reporting.

`Mount failure when already mounted` was strengthened at the same time. It previously
documented the broken behaviour as expected and asserted nothing about the mount
afterwards; it now asserts the mount survives, that the file system is still usable,
and that it unmounts cleanly.

## Execution Environments

### QEMU

**Verified.** ESP-IDF 5.5.3 ships `idf.py qemu`
(`tools/idf_py_actions/qemu_ext.py`); the emulator binary is installed separately with
`idf_tools.py install qemu-xtensa`. The test application boots to the Unity menu
unmodified, and in background mode `idf.py qemu` exposes the emulated UART on
**TCP port 5555** (`qemu_ext.py:338`), which is the automation hook — no firmware
change required.

QEMU emulates the Xtensa cores, SPI flash, UART, timers and eFuse. It does not emulate
the radio or anything analogue.

| Tag | Viable under QEMU | Reason |
|---|---|---|
| `[NvsManager]` | **Yes** (verified) | NVS is flash |
| `[FileSystem]` | **Yes** (verified, 11/11) | LittleFS sits on emulated flash |
| `[CoreDump]` | Likely | The core dump partition is flash and is detected correctly at boot; the deliberate panic and reboot were both observed to work |
| `[System]` | **No** (verified) | See below |
| `[WiFi]` | No | No radio emulation |
| `[Bluetooth]` | No | No radio emulation |
| `[Helpers]` | Restart only | Heap tracing needs JTAG |

**The ADC behaves more subtly than first assumed.** ADC *initialisation* is tolerated
under QEMU — `SystemRequestHandler::Setup()` is guarded by an `== ESP_OK` check and
degrades quietly, which is why the file system tests (which reach the file system
through `Esp32Interfaces::System` messages and therefore construct a
`SystemRequestHandler`) run fine. But an actual ADC *read* does not fail; it **hangs
the handler task indefinitely**. `[System]` therefore stalls rather than failing, and
a runner needs a per-selector timeout to catch it. An earlier draft of this document
predicted a clean assertion failure; that was wrong.

**Flash image state persists.** `qemu_flash.bin` is a raw drive image written in
place, so LittleFS contents, NVS and any core dump survive between runs. Successive
runs contaminate each other unless the runner restores a pristine image each time.
Generate one with `esptool merge-bin --fill-flash-size 4MB` over the bootloader,
partition table and application binaries.

The upside is that flash-image staging works as hoped: the `Prepare` / `Post file
system upgrade` pair can be staged by copying an image rather than reflashing a board,
and the core dump partition can be extracted directly from the image for inspection.

**How faithful is it?** On the evidence so far, more faithful than expected. QEMU
reproduced a use-after-free with the same backtrace addresses and the same faulting
address as hardware. That is one data point about one memory bug, and it says nothing
about concurrency: emulated scheduling is not cycle-accurate, so races that appear on
real silicon may still not reproduce, and the reverse. QEMU remains a fast regression
gate rather than a substitute for a bench run, and the two thirds of the suite covering
WiFi and Bluetooth is precisely where hardware behaviour is the thing under test.

### Hardware

A dedicated board wired to whichever machine runs the suite, plus an access point
matching the credentials in `unittest.config.json`. Someone has to own that hardware, the network,
and the triage of intermittent RF failures — an ongoing commitment rather than a
one-off setup, and the main argument for pushing as much as possible onto the emulator.

**Verified**: the board is driven over its console UART at 115200 baud with the same
expect-then-send protocol, resetting via DTR/RTS between runs to guarantee a fresh boot.

### Consequence

The set of tests that can run unattended and the set that runs under QEMU are nearly
identical, because both are defined by "touches no radio and no analogue". That means
the unattended tier can run on a hosted GitHub Actions runner with no bench machine and
no hardware to maintain — which removes the largest commitment from the plan.

The shape that falls out:

- **QEMU tier** — runs in CI on every push. `[NvsManager]` and `[FileSystem]` (once the
  defect above is resolved), plus `[CoreDump]` if it proves viable.
- **Hardware tier** — runs on the bench before a release. Everything else.

One runner drives both; the menu protocol does not care what is on the far end of the
serial port.

## Supplying Data to a Test

Tests can read from the console during execution using `unity_gets()`, declared in
`unity_config.h` alongside `unity_putc`. It is the same function the menu itself uses,
so it needs no configuration:

```c
char buffer[64];
printf("Iterations: ");
unity_gets(buffer, sizeof(buffer));
int iterations = atoi(buffer);
```

It blocks, echoes input, handles backspace, and terminates on `\r` or `\n`.

### Input Cannot Be Pre-Buffered

Before reading, `unity_gets()` discards whatever is already in the RX buffer
(`unity_port_esp32.c:87`). A runner that writes `"7\n50\n"` in a single operation loses
the `50`.

Every parameter therefore requires **expect-then-send**: the test prints a prompt, the
runner blocks until it sees that prompt, and only then writes the value. This makes the
prompt string part of each test's contract with the runner, so a convention should be
agreed early — something greppable such as `<<PARAM:iterations>>` — otherwise each test
invents its own and the runner accumulates special cases.

### Other Characteristics

- **No timeout.** A test waiting for input blocks indefinitely, and the read is a busy
  wait with no yield (`unity_port_esp32.c:44`), so it will saturate a core. This is why
  `unit_tests.c:57` notes that the task watchdog must be disabled. The same applies
  under QEMU, where it consumes a host core.
- **`unity_input_from_gdb`** (`unity_port_esp32.c:66`) is a documented back door for
  injecting input over a debugger without touching the console — useful for the JTAG
  and emulator paths.
- Any test calling `unity_gets()` becomes unrunnable by a bare `*` or tag sweep, because
  it will hang waiting for input. Such tests need either a sensible default on empty
  input or a dedicated tag that keeps them out of unattended runs.

### Where This Helps

- `TestBluetooth.cpp:806` already takes its iteration count from the BLE client; a
  console parameter would let the runner set it directly.
- `TestBluetooth.cpp:756` hardcodes 50 restarts. A parameter would allow 5 in CI and
  50 on the bench from a single test case rather than two.

## Proposed Firmware Changes

These move complexity out of the runner and into the tests, where it belongs.

1. **Convert ordered sequences to `TEST_CASE_MULTIPLE_STAGES`.** The four `[CoreDump]`
   cases and the file system upgrade pair currently encode their ordering implicitly.
   Expressing it in Unity moves sequencing and reboot resynchronisation into tooling
   that already understands it, and keeps the runner a thin driver rather than a place
   where test knowledge accumulates and rots.
2. ~~**Add a second tag axis.**~~ Done. Tests now carry `[Emulated]` when they suit an
   unattended emulated run and `[Slow]` when they are correct but too slow for every
   commit. Tag matching is a substring search, so the subsystem tags still select
   everything they did before and nothing is hidden from a developer. CI selects
   `[Emulated]`, so a new test opts in by being marked rather than by a list in the CI
   script being edited. Worth extending for the remaining cases — needs a peer, needs
   a reflash.
3. **Parameterise the long-running cases** via `unity_gets()`, using the agreed prompt
   convention, so iteration counts can differ between CI and the bench.

## Tooling Options

| Option | Notes |
|---|---|
| `pytest-embedded` | ESP-IDF's own harness. Provides `run_all_single_board_cases()` and `expect_unity_test_output()`, written against `unity_run_menu`, plus build/flash orchestration, reboot handling and JUnit XML. Not currently installed — `pip install pytest-embedded-idf pytest-embedded-serial-esp`. |
| Bespoke script | Roughly 150 lines: shell out to `build.sh`, open the transport, drive the menu, parse results. No new dependencies, and there is precedent in `test/SupportScripts/`. |

The bespoke route was taken. `TestRunner.py` handles the prompt protocol, reboot
detection, timeouts and JUnit output for both transports in a little over 250 lines,
and adds no dependency beyond pyserial, which is already present. `pytest-embedded`
remains the better answer if multi-stage tests or hardware fixtures grow complicated,
and nothing here prevents moving to it: the menu protocol is the stable interface.
